# Kluzar Outreach R2 setup

This guide covers the private `kluzar-outreach-files` bucket used by the Outreach Worker. Do not enable public bucket access or publish object URLs.

## 1. Confirm the bucket

In the Cloudflare dashboard, open **R2 Object Storage** and confirm the existing bucket is named `kluzar-outreach-files`. Keep public access disabled.

## 2. Bind the bucket to the Worker

Open the `outreach-api` Worker and add an R2 bucket binding:

- Variable name: `FILES`
- Bucket: `kluzar-outreach-files`

The checked-in Worker configuration also declares this binding. Keep the name consistent when configuring deployment.

## 3. Configure short-lived uploads

The Worker issues five-minute, SigV4-signed `PUT` URLs for individual staging keys only. Upload intents are tied to the authenticated user's workspace, expire after ten minutes, and are validated again by the Worker before a file is imported or made available. The Worker checks the exact byte count, content type, CSV encoding/format, and attachment signature, then copies validated bytes to a separate final key and deletes the staging object. This prevents a still-valid upload URL from overwriting an already-validated attachment. Downloads remain proxied through the Worker, which checks workspace ownership.

Create an R2 API token/key with **Object Read & Write** permissions scoped only to the `kluzar-outreach-files` bucket. Add these values to the `outreach-api` Worker's secret/variable store; never put the credentials in `wrangler.toml` or source control:

- `R2_ACCOUNT_ID`: the Cloudflare account ID
- `R2_ACCESS_KEY_ID`: the access key ID
- `R2_SECRET_ACCESS_KEY`: the secret access key (Worker secret)
- `R2_BUCKET_NAME`: `kluzar-outreach-files`

The existing `FILES` R2 binding remains required for server-side object validation and downloads. The S3 API credentials are used only to create scoped presigned upload URLs.

Configure an R2 lifecycle rule to expire objects under the `uploads/` prefix after one day. The Worker also removes expired staging objects during its scheduled cleanup; the lifecycle rule covers objects whose D1 intent was removed by a workspace/list deletion before cleanup.

## 4. Configure bucket CORS

Direct uploads require bucket CORS for the presigned request. Add one rule for the exact production origin:

- Allowed origin: `https://outreach.kluzar.com`
- Allowed method: `PUT`
- Allowed header: `Content-Type`
- Exposed headers: none
- Max age: `300` seconds

Do not use `*`, add other origins, allow `GET`/`DELETE`, or enable public bucket access. `frontend/public/_headers` allows only the Cloudflare R2 S3 endpoint family in `connect-src`; narrow that source to the account-specific `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com` host once the account ID is configured in the deployment's CSP.

## 5. Secrets and access

Keep R2 credentials and Worker secrets in Cloudflare's secret store, not in this repository. Rotate the key if it is exposed and revoke old keys. Grant bucket access only to the scoped Worker credential and administrators who need to manage the bucket. Do not log file contents, email addresses, object keys, or credentials.

## 6. Verify manually

1. Confirm public access remains disabled.
2. Confirm the Worker binding points to `kluzar-outreach-files`.
3. Configure the exact-origin CORS rule and Worker secrets above.
4. Upload a small test CSV through an authenticated workspace; confirm the browser's PUT goes to the signed R2 URL without sending cookies.
5. Confirm invalid format, mismatched size, expired intents, and unsupported attachments are rejected, and accepted files are not publicly reachable.
6. Confirm an authenticated user from another workspace cannot complete or download the object.
7. Delete test data after verification.
